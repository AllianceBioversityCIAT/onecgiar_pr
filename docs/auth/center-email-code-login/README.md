# Center email-code login — module reference

CGIAR **center staff who are not in the CGIAR Active Directory** sign in to PRMS with a 6-digit code e-mailed to them. The code is generated by PRMS-owned Cognito `CUSTOM_AUTH` triggers and delivered through PRMS's own notification pipeline, so it arrives from **"PRMS Reporting Tool" `<PRMS-No-reply@cgiar.org>`** and not from Cognito's default sender. Live on **TEST** since 2026-09-11/12; PROD is not configured yet.

> **Product rule (design `§18.5`):** a center user does **not** need a PRMS record before the first login. The first successful verify creates the PRMS user with the **guest** role from the ID-token claims — exactly as the CGIAR provider flow does. A brand-new guest then gets the normal `403 needsRoles` until an admin assigns roles; that is the expected first-login outcome, not a fault.

---

## Quick path

1. An admin sets the PRMS global parameter `OTP_ALLOWED_EMAIL_DOMAINS` (empty = the path is hidden).
2. The user opens `/login` → **"Continue with your Center account"** → types their center e-mail.
3. PRMS → AUTH microservice → Cognito `CUSTOM_AUTH` → the `CreateAuthChallenge` trigger mints the code and queues the e-mail.
4. The user types the code; PRMS returns the same session payload the password path returns.
5. Problem? → [`prod-rollout-runbook.md`](./prod-rollout-runbook.md) for configuration, and the spec's support triage (see [Operations](#9-operations)).

## 1. The three login paths on `/login`

| Path | Button | Who | Mechanism |
|---|---|---|---|
| CGIAR | "Continue with your CGIAR account" | Staff in the CGIAR directory | Azure AD / SAML via `cognito.loginWithAzureAd()` |
| **Center** | "Continue with your Center account" | Center staff outside AD, domain in the allow-list | **This module** — e-mailed 6-digit code |
| External | "Continue as an external user" | Non-CGIAR accounts | E-mail + password (`loginWithCredentials()`) |

Only one path is open at a time (`LoginComponent` hides the Center panel while the external or password-change form is open). The Center block renders **only** when `GET auth/login/otp/config` returns a non-empty `domains` array.

## 2. End-to-end sequence

| # | Actor | Call / event |
|---|---|---|
| 1 | PRMS client | `GET auth/login/otp/config` → `{ domains: string[] }`; renders the Center block, validates the typed domain locally |
| 2 | PRMS client → PRMS server | `POST auth/login/otp/start { email }` |
| 3 | PRMS server (`startOtp`) | `OtpThrottlerGuard` counts the request first (route guard, 5 / 15 min per e-mail — even requests later rejected for their domain consume a slot) → `startOtp`: normalise → allow-list (else `400`) → user lookup; **inactive** user → neutral `200` with a signed **decoy** session, no upstream call |
| 4 | PRMS server → AUTH microservice | `POST /auth/login/otp/start { username }` (MIS-authenticated) |
| 5 | AUTH microservice → Cognito | `InitiateAuth { AuthFlow: CUSTOM_AUTH, ClientId, AuthParameters: { USERNAME, SECRET_HASH } }` |
| 6 | Cognito → **DefineAuthChallenge** | no session → `CUSTOM_CHALLENGE`, `issueTokens = false`; `userNotFound` → still a (fake) challenge |
| 7 | Cognito → **CreateAuthChallenge** | reuse the code carried in `challengeMetadata` (`CODE-<code>`) **or** mint a fresh `crypto.randomInt` 6-digit code → `privateChallengeParameters.answer`, masked `destination`; **only for a fresh code** publish the e-mail |
| 8 | Trigger → RabbitMQ | `sendToQueue(MS_NOTIFICATION_QUEUE, { pattern: 'send', data: { auth, data: ConfigMessageDto } })`, confirm channel, `persistent: true` |
| 9 | notification-microservice → SMTP | subject *"Your PRMS Reporting Tool sign-in code"*, from `PRMS-No-reply@cgiar.org` / name "PRMS Reporting Tool" |
| 10 | PRMS client → PRMS server | `POST auth/login/otp/verify { email, code, session }` |
| 11 | PRMS server → microservice → Cognito | `RespondToAuthChallenge { ChallengeName: CUSTOM_CHALLENGE, Session, ChallengeResponses: { USERNAME, ANSWER, SECRET_HASH } }` |
| 12 | Cognito → **VerifyAuthChallengeResponse** | `answerCorrect = timingSafeEqual(answer, stored)` |
| 13 | Cognito → DefineAuthChallenge | correct → `issueTokens`; wrong and `< 3` rounds → new `CUSTOM_CHALLENGE` with a **rotated session**, same code; wrong at 3 → `failAuthentication` |
| 14 | PRMS server | tokens → `createOrUpdateUserFromAuthProvider` (creates the guest user if new) → `last_login` → `createSuccessfulLoginResponse(user, tokens)` — byte-identical to `/login/custom` |

**Wrong code is not an exception in `CUSTOM_AUTH`.** A reply with `ChallengeName = CUSTOM_CHALLENGE` and no `AuthenticationResult` is mapped to `CODE_MISMATCH` and the **rotated session is returned to the client**, which must store it before retrying. A decoy mismatch mints a fresh decoy session too, so both bodies carry the same key set.

## 4. Configuration

| Where | Setting | Value / rule |
|---|---|---|
| PRMS DB | `global_parameters.OTP_ALLOWED_EMAIL_DOMAINS`, category `platform_global_variables` | Comma-separated, lower-case, no `@`. **Empty = the Center path is hidden.** Read through `GlobalParameterCacheService` with a **60 s** staleness window |
| AUTH microservice env | `PASSWORDLESS_DOMAINS` | Same domains as above — **must match** (see the dual allow-list rule). TEST: `cifor-icraf.org,icrisat.org` |
| Cognito pool | `LambdaConfig.{DefineAuthChallenge, CreateAuthChallenge, VerifyAuthChallengeResponse}` | The three trigger ARNs. Pool-level, but inert for every client without `ALLOW_CUSTOM_AUTH` |
| Cognito app client | `general-client` `AuthSessionValidity` | **5 minutes** (raised from 3) — this *is* the code's lifetime |
| Cognito app client | `ExplicitAuthFlows` must include `ALLOW_CUSTOM_AUTH` | Only `general-client` has it on the TEST pool (9 siblings unaffected) |
| Trigger env | `MS_NOTIFICATION_HOST` **or** `MS_RMQ_HOST` + `MS_RMQ_USER` + `MS_RMQ_PASSWORD` | Full broker URL wins; otherwise assembled as `amqps://<user>:<pass>@<host>`, credentials percent-encoded, **no path segment** |
| Trigger env | `MS_NOTIFICATION_QUEUE` | Queue the notification microservice consumes (`send` pattern) |
| Trigger env | `MS_NOTIFICATION_USER` / `MS_NOTIFICATION_PASSWORD` | CLARISA application credentials the consumer's `AuthInterceptor` validates |
| Trigger env | `EMAIL_SENDER` | `PRMS-No-reply@cgiar.org` |
| Trigger env | `APP_URL` | Footer link; defaults to `https://reporting.cgiar.org/` |

**The PROD pool does not need the `EMAIL_OTP` first-auth factor.** TEST carried it only for the initial spike and it was rolled back on 2026-09-11; the net pool change since the spec started is the three triggers.

## 5. API contracts

### 5.1 PRMS server (public, no JWT middleware — `/auth/*` is outside its mounts)

| Route | Request | Success | Errors |
|---|---|---|---|
| `GET auth/login/otp/config` | — | `200 { response: { domains: string[] }, message, status }` | — |
| `POST auth/login/otp/start` | `{ email }` (`IsEmail`, `MaxLength(254)`) | `200 { response: { sent: true, session, destination }, message: 'If this account exists, a code has been sent.' }` — **byte-identical for known and unknown users** | `400 OTP_DOMAIN_NOT_ALLOWED` · `429 OTP_RATE_LIMITED` · `503 OTP_UPSTREAM_UNAVAILABLE` |
| `POST auth/login/otp/verify` | `{ email, code (/^\d{4,10}$/), session }` | `200` exactly the `/login/custom` shape: `{ valid: true, token, user, auth_tokens }` | `401 OTP_CODE_MISMATCH` (**carries the rotated `session`**) · `401 OTP_CODE_EXPIRED` · `401 OTP_ATTEMPTS_EXCEEDED` · `401 OTP_NOT_AUTHORIZED` · `403 needsRoles` · `429` · `503` |

### 5.2 AUTH microservice (MIS-authenticated, generic `username`)

| Route | Request | Success (`201`) | Errors |
|---|---|---|---|
| `POST /auth/login/otp/start` | `{ username }` | `{ challengeName: 'CUSTOM_CHALLENGE', session, codeDeliveryDestination? }` | `401 { code: ATTEMPTS_EXCEEDED \| NOT_AUTHORIZED \| CHALLENGE_NOT_SUPPORTED }` · `502 { code: UPSTREAM_ERROR }` |
| `POST /auth/login/otp/verify` | `{ username, code, session }` | `{ tokens: { accessToken, idToken, refreshToken, expiresIn, tokenType } }` | `401 { code: CODE_MISMATCH, session }` · `401 { code: CODE_EXPIRED \| ATTEMPTS_EXCEEDED \| NOT_AUTHORIZED \| CHALLENGE_NOT_SUPPORTED }` · `502 { code: UPSTREAM_ERROR }` |

Error bodies are `{ statusCode, code, message, path, timestamp }`; `message` is stable copy from `CognitoService.OTP_ERROR_COPY`, never raw Cognito text.

## 6. Security model

| Control | Detail |
|---|---|
| Allow-list | Domain must be in `OTP_ALLOWED_EMAIL_DOMAINS`; the domain is public knowledge (it is on the button), so a foreign domain gets a helpful `400` |
| Decoy sessions | **Inactive** PRMS users get a server-signed decoy (HMAC-SHA256 over `email\|nonce\|exp` keyed with `JWT_SKEY`, base64url, length jittered 1,400–1,700, `exp` bytes XOR-masked). Verified with `timingSafeEqual`; a verified decoy answers `401 OTP_CODE_MISMATCH` with a fresh decoy session — indistinguishable from a real wrong code |
| Enumeration resistance | Cognito `PreventUserExistenceErrors=ENABLED` + the `userNotFound` branch of `DefineAuthChallenge` return a **fake challenge** with a random masked destination and no e-mail. The trigger even logs the same `code_sent` outcome, so CloudWatch cannot be used to enumerate |
| Throttling | `OtpThrottlerGuard`: **5 start / 10 verify per 15 min per normalised e-mail** (fallback `x-forwarded-for`, then `req.ip`), counted **before** the user lookup. In-memory, **per instance** |
| Cognito-side limits | **3 attempts per session**; code lifetime = `AuthSessionValidity` = **5 min**; a session is single-use |
| Constant time | `VerifyAuthChallengeResponse` and the PRMS decoy check both use `timingSafeEqual` |
| Log hygiene | Never the code, address, session, tokens, `challengeMetadata` or broker credentials. Trigger fields are an **allow-list** in `lib/logger.ts`; the microservice's `LoggingInterceptor` runs `redactSensitive()` over the response preview (`session`, `tokens`, `accessToken`, `idToken`, `refreshToken`, `password`, `temporaryPassword`, `secretHash`, `code`, any casing/depth) |

## 8. Operations

**Support triage — "code not received."** Work the table in the spec runbook (`docs/specs/changes/cognito-email-otp-login/runbook/cognito-email-otp.md`, section *Support runbook — "code not received" triage*) in order: allow-list → inactive PRMS user → **missing Cognito user** (the only account reason a code never arrives since first-login auto-provisioning) → `FORCE_CHANGE_PASSWORD` → mailbox/spam → rate limited.

**Provisioning center users.** An admin registers them through PRMS → the microservice's `/auth/register` → for a domain in `PASSWORDLESS_DOMAINS`, `AdminCreateUser` runs **without** `TemporaryPassword`, `MessageAction: SUPPRESS`, `email_verified=true` → the user lands `CONFIRMED` and is eligible for the code path immediately. A user created directly in Cognito can sign in too.

**Dual allow-list rule.** `OTP_ALLOWED_EMAIL_DOMAINS` (PRMS) and `PASSWORDLESS_DOMAINS` (microservice env) **must be changed together**. A domain present only in PRMS lets the user reach the button but provisions them with a temporary password → `FORCE_CHANGE_PASSWORD` → their Center login can never succeed.

## 9. Known limits & follow-ups

Summarised from `design.md` §13 and §18.5.

| # | Item | State |
|---|---|---|
| a | Rate limiting is in-memory **per instance** for both e-mail and IP | Accepted; move to a shared store before horizontal scaling |
| b | With `JWT_SKEY` unset the decoy key is per-process random — a decoy minted on one instance degrades to `OTP_NOT_AUTHORIZED` on another | Only in environments missing a required env var |
| c | Response timing between known and unknown users is not equalised | Accepted for this population |
| d | While the microservice is down, a known user gets `503` but the decoy path still answers `200` | Outage-time existence channel; accepted |
| e | `auth.otp.*` logs at info level with `domain` only (not `debug`) | Deliberate, so CloudWatch triage works |
| f | Decoy charset bias: segment tails can only take 16/16/4 alphabet values (p ≈ 1/256 classifier) | **Cheap fix before PROD** — randomise the unused bits, add key domain separation |
| g | Unknown-user destination mask in `CreateAuthChallenge` is random (`b***@g***`) instead of derived from `event.userName` | Not client-visible today; **fix before PROD** |
| h | No provisioning e-mail for passwordless users — the new user is never told the account exists | Follow-up: PRMS sends an account-created e-mail pointing at the Center path |
| i | Dual allow-list must be edited in two places | Follow-up: derive one from the other (`passwordless: true` flag on `/auth/register`) |
| j | Pre-existing a11y gap: `/login`'s `.global-link` support link is 15 px tall (< 24 px, WCAG 2.5.8) | Separate hygiene change |
| k | Sonar counts spec files as new code in `one-cgiar-microservices` | Configure `sonar.test.inclusions` |
| l | At `verify`, an *inactive* PRMS user is distinguishable from an unknown one | Recorded, not fixed — no active user is exposed |
| m | Offering the code path to existing external users; federation of the center tenants | Strategic follow-ups |
