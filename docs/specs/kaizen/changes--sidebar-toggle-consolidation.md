## Lessons

- **KZ-STC-1 — A spec that changes a shared DOM contract inventoried only its *unit-test* consumers, so an existing E2E suite on the same surface was broken silently.** (Product, **High**)
  - Root cause: `design.md` §10's Testing Plan and `tasks.md`'s expected-file lists were derived from the Jest specs co-located with the two components. Nothing grepped `cypress/e2e/**` for consumers of `[data-guide="sidebar-toggle"]`. `cypress/e2e/result-detail/sidebar-collapse.cy.ts` — written by the immediately preceding spec, one day earlier — hard-codes `header.pr-shell-topbar [data-guide="sidebar-toggle"]` at line 44 and uses it at lines 152, 192, 216. Removing the topbar button reduced that selector to zero matches, breaking 3 of its 5 tests.
  - Compounding factor: `design.md` §13 positively asserted *"No automated coverage for `driver.js` anchor-timing races in this codebase today… would require a headless-browser/Cypress spec… which is disproportionate to a Lite change."* That suite already asserted `.driver-popover` visibility and title text at both viewport bands. The spec therefore recorded a **manual-only verification gap** (`requirements.md` §8) for a check that was ~80% automated already — and the false premise, not the missing file, is what let the omission through review twice.
  - Why review did not catch it: the suite is **dormant** — `describeWithToken` (`cypress/support/result-detail.ts:40`) degrades to `describe.skip` without a configured `userToken`, and Cypress is not in CI. Nothing went red. Both Reviewers were pointed at the Jest specs the approved `design.md` §10 named.
  - Evidence: `execution.md` → *Pivot Record* §1/§2/§3 and *Pivot Resolution*; `design.md` §10, §13; `requirements.md` §8; `docs/specs/kaizen/changes--result-sidebar-collapse-mobile.md`.
  - Standardization → P1 (pending item 1).

- **KZ-STC-2 — A pending kaizen standardization can be invalidated by a later spec before the backlog is ever applied, and nothing re-validates it at apply time.** (Methodology, **High**)
  - Root cause: pending items are captured as *verbatim text to write*, with no re-verification step between capture and application. The backlog is append-only and unaware of subsequent commits, so an item can silently rot from "correct" to "false."
  - Concrete instance, one day old: `docs/specs/kaizen/changes--result-sidebar-collapse-mobile.md` pending item **#2** (`guide-sync`, Medium) instructs adding to `shell-topbar/CLAUDE.md`: *"The toggle button also carries `data-guide="sidebar-toggle"` … the always-visible anchor for the result-sidebar discoverability hint … so exactly one anchor is ever present regardless of sidebar state."* **This spec deleted that button.** Applying that item verbatim on `master` would write a factual falsehood into a component guide — the precise failure mode the factual-claims sweep (`/akili-archive` Step 3 item 3) exists to prevent, arriving through the mechanism meant to fix it.
  - Note the asymmetry that makes this dangerous: the *spec* documents got a Correction Closure sweep when the Pivot fired, but the *kaizen backlog* referencing the same superseded fact did not, because nothing links a pivot to the pending items that depend on it.
  - Evidence: `changes--result-sidebar-collapse-mobile.md` §Pending Items row 2; this spec's `execution.md` → *Pivot Resolution* → Known residue.
  - Methodology lesson → **no local edit.** Upstream to the AKILI methodology repo: the apply phase should re-verify each pending item against current `HEAD` before writing, and entry files should support a `superseded` status. Local consequence recorded as pending item 4.

## Noted, not a lesson

- **The `[~]` discipline worked under real pressure.** `STC-T-2` sat at `[~]` for a full day on a Reviewer PASS because its manual criterion was genuinely outstanding, and moved to `[x]` only after a human performed the check. Step 2.3.0 behaved exactly as designed; no gap.
- **Advisories were contained.** Eight were recorded, none gated, none folded into the spec — including one (the weak `@if` substring assertion) that arguably weakens a gate. It was escalated to the user as an option rather than silently fixed. Correct application of *Advisory Never Becomes A Task*; the rule held precisely where it was tempting to break it.
- **The Pivot was raised on a fully-green run.** Both tasks had passed review and every automated gate was green when it fired. Worth noting because it is the case most likely to be waved through: nothing was failing, so nothing forced the stop except reading the evidence.
- **A cross-spec review blind spot, not a Reviewer failure.** Both Reviewers were given diffs plus pointers to the documents the approved spec named. Neither was briefed to grep for out-of-spec consumers, and neither had the predecessor spec in context. The fix belongs in the spec's Testing Plan (KZ-STC-1), not in the Reviewer persona.
