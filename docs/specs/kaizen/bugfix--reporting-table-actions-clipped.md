## Lessons

- **KZ-RTA-1 — A CSS change reasoned about correctly for its own paint consequences can still silently break something else that resolves geometry against the same box, and the spec's own contract named the risk without connecting it to a specific hazard.** (Product, High)
  - Root cause: across the sticky rework's three attempts, every non-trivial finding shared one shape. Attempt 1 set opaque backgrounds on the pinned cells without checking their actual rendered height against the row's border (a near-miss, closed cleanly). Attempt 2's real regression: widening the pinned cells to absorb the row's gutter (`margin-right: -20px`) silently moved the containing-block edge that the "···" row-menu popover's `position: absolute; right: 0` resolves against — production and attempt 1 placed the popover 20px inboard of the card edge; attempt 2 placed it flush against it, because nothing in the attempt-2 package checked what else was measured *from* the boxes being widened. `design.md`'s own `RTA-DD-2` Implementation contract named the gutter arithmetic (item 1) and named the popover as a re-verification duty (item 5) — as two separate bullets — but never asked the connecting question: *what else in this component resolves its position or size against the exact boxes this task is about to resize?* That is the actual gap, not an implementer oversight — the same shape of defect recurred across attempts precisely because nothing in the task's own contract asked that question once, in one place.
  - Evidence: `execution.md` lines 433-439 (attempt 2's Reviewer finding, verbatim) and lines 479-483 (the run's own root-cause hypothesis, which explicitly names this "the kaizen candidate from this run").
  - Standardization → P1: a CSS task that resizes, repositions, or changes the containing-block behavior of an existing element (e.g. `position: relative` → `sticky`, widening a box, absorbing a gutter) should require one explicit question in its own Definition of Done: *"what other element in this file/component resolves its own position, size, or `right`/`bottom`/`left`/`top` value against this element or its ancestor chain?"* — answered by a grep for `position: absolute` and `right:`/`bottom:` scoped to descendants, not assumed clean because the diff's own paint result looks correct.

- **KZ-RTA-2 — `cy.get(...).should('be.visible')` does not check clip-region containment by an ancestor's `overflow`, and can pass on an element that is almost entirely clipped.** (Product, High)
  - Root cause: the pre-existing CT suite asserted `cy.get('[role="menu"]').should('be.visible')` for the row's overflow menu, and this assertion passed even though the menu — a `position: absolute` popover inside a `overflow-y: hidden` scroller — was ~76% clipped (only a ~38px sliver of a 158px popover fell inside the clip rectangle, confirmed by direct `getBoundingClientRect()` measurement against the scroller's bounds). Cypress's visibility heuristic checks `opacity`/`display`/DOM detachment/basic occlusion by an overlapping element — it does not check whether an ancestor's `overflow` clips the element's own rendered box. This is exactly the false-positive class `design.md` had already predicted in the abstract ("a presence-assertion would prove the class was added, not that the button is reachable") but it slipped in anyway, through an assertion that reads as behavioral rather than as presence-only.
  - Evidence: `execution.md` lines 368-376 ("🚨 The more important finding: RTA-T-2's menu assertion is a false positive") and lines 600-602 (the companion finding recorded on the separate production-defect ticket).
  - Standardization → P2: any Cypress assertion of the form `should('be.visible')` on an element that sits inside an ancestor with `overflow: hidden`/`auto` MUST NOT be treated as proof the element is fully reachable/visible — `be.visible` proves paintability, not clip-region containment. Where clip-region containment is the actual property under test (a popover, a sticky/pinned region, anything near a scroll boundary), compare the element's `getBoundingClientRect()` against its clipping ancestor's client bounds directly, the way this spec's own `RTA-T-2` amendment did.
