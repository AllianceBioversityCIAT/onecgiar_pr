## 3.5 Reopened — user-reported regression at normal desktop width (post-close)

**Date:** 2026-09-03, immediately after the task above was marked `[x]` and reported to the user.

**User report (screenshot, ~1911×952 real browser window — NOT a constrained laptop viewport):** the Cancel/Add evidence buttons render on top of / overlapping form text; the modal appears cut, with content ("...number, slide number, table number)" label + textarea start) visible *below* the footer buttons instead of scrolled away above them. The title "Add New Evidence" also visually collides with "Source of the evidence".

**Root cause (Leader analysis, confirmed by reading the current `.evidence_modal` SCSS again):** DD-1's sticky approach anchors `.modal_header`/`.buttons` to `.evidence_modal`'s own scrolling box (`overflow-y: auto; max-height: 85vh`). But `.evidence_modal` sits inside `.pr-dialog__body` inside `.pr-dialog`, which has its **own** independent `max-height: 90vh; overflow: auto`. Whenever the popup's content is short enough to fit inside `.evidence_modal`'s 85vh cap without needing `.evidence_modal`'s own internal scroll, `.evidence_modal.scrollTop` never moves — instead the **outer** `.pr-dialog` becomes the element that actually scrolls (dragging the entire `.evidence_modal` block, header/body/footer together, as one unit). Since `position: sticky` only reacts to scrolling of its own nearest scrolling ancestor (`.evidence_modal`), and that ancestor isn't the one moving, the header/buttons get **no pinning effect at all** in this case — they just ride along with the rest of the block, producing exactly the overlap/cut-off the user saw. This is a materially worse manifestation of the "DD-1 residual risk" the Reviewer flagged as ADVISORY (they estimated a bounded ~5-10px overflow near 600-700px viewport heights; in practice, at a normal ~950px-tall window, the ambiguity between the two independently-capped scroll containers breaks the pinning outright, not just by a few px).

**Decision:** apply the design's own pre-authorized fallback — `design.md` EVM-DD-2 — instead of continuing to patch DD-1. Eliminate the second (ambiguous) scrolling ancestor entirely:
- Wrap `<app-evidence-item>` in a new `.modal_body` element; move `overflow-y: auto` from `.evidence_modal` onto `.modal_body`, with `.modal_body { flex: 1; min-height: 0; }` so it fills the space between header and footer inside a now-bounded `.evidence_modal`.
- `.evidence_modal` keeps its `max-height: 85vh` (still under the outer `.pr-dialog`'s 90vh) but changes `overflow-y: auto` → `hidden` (or removes it) — it is no longer itself a scrolling ancestor, only a size cap.
- `.modal_header` / `.buttons` drop `position: sticky` entirely — they become plain, non-scrolling flex children of a flex column whose only scrolling descendant is `.modal_body`. There is now exactly one scrolling ancestor in the whole popup subtree, so there is no ambiguity left for anything to anchor against incorrectly.

**Effort bumped:** medium → high (per `.agents/leader.md` — a failed fix is usually under-thinking; this failure was a real user-facing regression found after a Reviewer PASS, so the retry gets deeper scrutiny including a real desktop-width live check, not just the constrained-viewport one).

## 3.6 Attempt 3 (Leader-inline) — dialog header rendering behind the app shell's fixed top bar

**Date:** 2026-09-03, after attempt 2 was reported complete. **User report (screenshot):** with attempt 2 live, the popup's title ("Add New Evidence") and close ✕ were still not visible — the dialog appeared cut off at the top, its rounded top border missing. This is a **different defect** from the attempt-1/2 double-scroll bug (already fixed and unaffected here) — this one is about the dialog's *initial vertical position*, not its scroll behavior.

**Investigation (Leader, live in the user's own already-running local server/client — reused rather than starting a competing instance):**
- Confirmed via `getBoundingClientRect()` that `.pr-dialog-mask` (`position: fixed; inset: 0`) genuinely spans the full viewport (top=0) with no stacking-context-creating ancestor between it and `document.body` (checked every ancestor for `transform`/`filter`/`isolation`/`position+z-index≠auto` — none found).
- Confirmed via `document.elementsFromPoint()` that the app shell's sticky header (`.app-shell-header`, `position: sticky; z-index: 30` in `app.component.scss`, containing the search bar and the test-environment banner, ~108px tall together) paints **above** `.pr-dialog-mask` (`z-index: 1100`) at the same screen point — the reverse of what z-index alone would predict.
- **Ruled out a fixable z-index/stacking-context issue empirically**: raising `.pr-dialog-mask`'s z-index live (2000 → 1,000,000) via `element.style.zIndex` produced **no change** to which element won hit-testing or paint order at the overlap point. `transform: translateZ(0)`, `will-change: transform`, and `isolation: isolate` on the mask were also tried live — none changed the outcome. This points to a Chromium compositing-layer-ordering quirk specific to a `position: sticky` ancestor rendering above a deeply-nested `position: fixed` descendant when neither establishes a stacking context relative to the other in the normal DOM tree — `pr-dialog` renders inline in the component tree (its own docstring notes this was a deliberate choice, not via a CDK-overlay-style portal to `document.body`), which is what exposes it to this class of bug. **Root-causing the compositing quirk itself, or moving `pr-dialog` to a true body-appended portal, is out of scope for this spec** (`requirements.md` §3 explicitly excludes `pr-dialog.component.ts/scss` changes) and was not pursued further.
- **The fix that doesn't require touching `pr-dialog` at all:** since the occlusion only happens where the two elements' rectangles overlap, capping `.evidence_modal`'s height so the dialog's vertically-centered top edge can never reach into the shell header's ~108px band eliminates the symptom regardless of the underlying compositing mystery. Measured `.app-shell-header`'s real height live (108.1px total: banner 52.1px + topbar 56.0px) to size the buffer.

**Fix applied (Leader-inline — single-file, single-declaration change, self-verified live; within the Leader's punctual-verification/1-file-edit threshold, not delegated):**
- `rd-evidences.component.scss` — `.evidence_modal`'s `max-height: 85vh` → `max-height: min(85vh, calc(100vh - 300px))`. This guarantees ≥130px of clearance above the mask's centered top edge on any viewport (comfortably above the ~108px worst case), while `85vh` remains the effective cap on generously-tall viewports where the fixed buffer isn't the binding constraint.
- `rd-evidences.component.spec.ts` — updated the one test asserting the literal `max-height: 85vh` string to assert the new `min(85vh, calc(100vh - 300px))` value instead (with an explanatory comment); no other test needed to change since the DD-2 structural assertions (`.modal_body` scrolling, no `position: sticky`, etc.) are independent of the exact max-height formula.
- `rd-evidences/CLAUDE.md` — new Trampas entry documenting the compositing quirk, why z-index tuning doesn't work, and why the fix lives in `rd-evidences` rather than `pr-dialog`; `Verified:` re-stamped to attempt 3.

**Live re-verification (Leader, same session, reusing the user's running server on :3400 / client on :4200 — no local processes started or stopped by the Leader this round):**

## 3.7 Attempt 4 (Leader-inline) — density/UX pass: default source selection + spacing

**Date:** 2026-09-03, after attempt 3. **User feedback (two follow-up messages with screenshots):** (1) with the popup now correctly clamped, the user asked for it to use more of the available screen height, and separately to reduce the spacing between form questions to cut scrolling; (2) pointed out the "Source of the evidence" radio group renders with neither option visually selected even though a Link field is already showing below it — inconsistent/confusing; (3) a stronger follow-up after seeing the still-small popup: "this is not user-friendly at all... too much scroll," asking for a real density pass.

**Investigation & fixes (Leader-inline, live in the user's own running server/client):**

1. **Default source selection was silently broken.** `rd-evidences.component.ts` already initializes `draftEvidence = { is_sharepoint: false }` (intending "Link" as the default), but `evidence-item.component.ts`'s `evidencesType` used numeric `id: 0` (Link) / `id: 1` (Upload file). `pr-radio-button` selects an option via strict equality (`value === option[optionValue]`); `false === 0` is `false` in JS, so **neither** radio ever showed as checked, regardless of `is_sharepoint`'s value — a genuine pre-existing bug, not just a missing default. Fixed by changing `evidencesType` to `{ id: false, name: 'Link' }` / `{ id: true, name: 'Upload file' }`, matching `is_sharepoint`'s actual boolean type. Verified `cleanSource(e)`'s `if (e) / else` branch is unaffected (boolean truthiness matches the old 0/1 truthiness exactly) and no other code reads `evidencesType`'s `id` as a number.
2. **Measured the real source of "too much scroll" live** rather than guessing: walked `.evidence_fields`'s children via `getBoundingClientRect()`, found `.link`'s rendered height (110px) came from `app-pr-input` itself, then traced that to `.field_card`'s global `margin: 20px 0` (`src/styles/field-card.scss`, shared by `pr-input`/`pr-textarea`/`pr-radio-button` app-wide) — which **stacks** with `.evidence_fields`'s own flex `gap` instead of being replaced by it. Two adjacent fields ended up `20px + gap + 20px` apart — the single biggest contributor to the form's height, larger than the `gap` value itself.
3. **Fixes applied, in order of impact:**
   - `evidence-item.component.scss`, inside `.evidence_item.embedded`: added a **scoped** `::ng-deep .field_card { margin: 4px 0; }` override — only affects `.field_card` instances rendered inside an `embedded` `evidence-item` (this popup, and any other embedded usage), leaves `src/styles/field-card.scss`'s global 20px margin untouched for every other consumer app-wide. This is the highest-impact single change.
   - `evidence-item.component.scss`: `.evidence_fields`'s `gap` 24px → 16px.
   - `rd-evidences.component.scss`: `.evidence_modal`'s own `gap` 24px → 20px.
   - `rd-evidences.component.scss`: attempt 3's height-buffer trimmed `calc(100vh - 300px)` → `calc(100vh - 260px)` (still ≥120px clearance above the measured 108px shell-header worst case, verified live again after the change: 21.9px clearance held at the sandbox's constrained 575px-viewport test).
4. **Measured impact live:** with the new spacing, the form's natural (uncapped) content height dropped from ~858px (attempt 1/2 baseline) to **730px** — a ~128px reduction from the `.field_card`/gap fixes alone, on top of what attempts 2–3 had already fixed structurally. Full elimination of scrolling for a 4-6-question form is not achievable within the fixed header-clearance constraint on short screens (a hard trade-off against the attempt-3 fix, not a regression of it), but scrolling is now substantially reduced and the popup no longer looks anomalously undersized when content is short.
