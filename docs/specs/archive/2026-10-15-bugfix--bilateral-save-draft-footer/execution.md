### Pivot resolution — `BSF-T-1` reclassified (2026-10-15)

The user supplied real screenshots of the actual reported defect ("así es como se muestra" vs. "así es como debería"), showing: in Policy Change's Type-Specific Detail, the `app-field-card` header's save-state pill (and the `REQUIRED` badge) render as a bare dot icon with **no visible text** on the Policy type, USD amount, and Status fields — instead of the full "Unsaved changes" pill the rest of the app shows. This is **not** the footer "Save draft" button at all — the original QA report's "Save Changes button is not fully displayed" almost certainly describes this field-level pill truncation, not the footer control the two prior Implementer attempts spent ~120 tool calls trying (and failing) to reproduce.

**Root cause, confirmed by direct read (not re-derived from a citation):**
- `src/styles/field-card.scss:67-181` — `.field_card_header` is an un-wrapped flex row. `.fch_save` (the save-state pill) is `flex: none` + `white-space: nowrap`; `.fch_required` (the REQUIRED badge) is `flex-shrink: 0`. Only `.fch_title` (the field label) is allowed to shrink (`min-width: 0`).
- When the combined intrinsic width of the non-shrinking badge + pill exceeds the available header width, the flex row overflows its container even with the title shrunk to nothing — and the pill, pushed to the far right via `margin-left: auto`, gets visually clipped, showing only its leading icon.
- **This is a direct, self-inflicted regression from `PCP-T-1`** (this same session, `bugfix/policy-change-usd-amount-position`, already shipped): grouping Policy type + USD amount + Status into one `grid-cols-[repeat(auto-fit,minmax(190px,1fr))]` row made each field's column far narrower than before — narrow enough that the header's non-shrinking elements (badge + pill) no longer fit, which they did when Policy type stood alone at full row width.

**Resolution:** the footer-button-clipping premise (`BSF-R-1`/`BSF-AC-1`, `design.md` P-2/P-3) is **abandoned as the wrong target** — two thorough attempts correctly found no defect there because there wasn't one. `BSF-T-1` is closed as **superseded**, not completed and not re-attempted under its original scope. The real, now-confirmed defect is moved to a new, correctly-scoped spec: `docs/specs/bugfix/field-card-save-pill-truncation/`. #### Attempt 1 — Reviewer verdict: `FAIL`

**STATUS: FAIL**

Summary: the diff fixes the stale-error case (`BSF-AC-2`) for every section that saves through `flush()` — but it breaks `BSF-R-3`/`BSF-AC-3` for the **Evidence** section specifically, found by reading the code (no test covers it, which is itself part of the gap).

1. **Discovered Issue:** `pendingStatusKeysFor` misses Evidence entirely. `SECTION_ENDPOINT_KEYS.evidence = []` (`bilateral-auto-save.service.ts:47`) — Evidence never goes into `_pendingFields`/`_pendingPayloads`. Its save runs a separate path (`manualSave$` → `saveSection()` → `runImmediate('evidence', …)` in `section-evidence.component.ts:191-195, 463`), which sets `fieldStatus['evidence']` directly. So `flushTargets` is always `[]` for Evidence, `hasErrorForFields([])` is always `false`, and `waitForSectionSave('evidence', [])` loops the full 15s timeout on a genuine Evidence save failure, which `triggerManualSave()` then reports as success/up-to-date instead of "Save failed." Before this fix, `hasErrorFor(section)` had an explicit Evidence branch (`service.ts:324`) that caught exactly this case — the new scoped path lost it.
   - **Violated Rule:** `requirements.md` `BSF-R-3`/`BSF-AC-3` (a current-flush failure must still report promptly); `design.md` §2.3 Reversion Challenge's own premise ("a field that genuinely fails as part of the current flush is, by construction, included in the scoped field set" — false for Evidence).
   - **Remediation Suggestion:** make `pendingStatusKeysFor('evidence')` return `['evidence']` (Evidence's Save draft always re-runs the whole section, so `'evidence'` is always this flush's target) — or special-case `section === 'evidence'` the same way `hasErrorFor`/`hasPendingFor` already do. Confirm `lastErrorMessageForFields(['evidence'])` falls back cleanly. Add a test: active section `evidence`, `runImmediate('evidence')` fails, assert "Save failed" shows and the call returns well under 15s.

**ADVISORY (non-gating):** (a) the falsifier test's "RED" claim is technically a setup-absence red (the new methods didn't exist pre-fix), not a behavioral red — the component test's mechanism-lock assertion is the real behavioral lock; record this distinction accurately rather than as claimed; (b) doc comments citing line numbers (`line ~867`, `~1047`) will drift — name methods, not lines; (c) in read-only mode, `pendingStatusKeysFor` could theoretically over-include compared to what `flush()` actually sends — currently harmless (read-only staging already filters to exempt keys), but sharing one filter would prevent future drift.
