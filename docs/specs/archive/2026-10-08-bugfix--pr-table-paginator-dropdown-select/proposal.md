## 2. Intent

Make every table's rows-per-page dropdown in the system visually display the page size that is actually in effect, instead of silently showing the first configured option regardless of the real value.

## 3. Problem / Current Behavior

- The bilateral results table (`/bilateral/:centerAcronym`) was changed on 2026-09-29 (commit `bd37a0f31`, `[SPEC:quick/bilateral-results-default-100-rows]`) to default to **100 rows per page** instead of 10 — citation as run: `git show bd37a0f31 -- onecgiar-pr-client/src/app/pages/bilateral/pages/bilateral-results-list/bilateral-results-list.component.html` shows `[rows]="10"` → `[rows]="100"`, options unchanged at `[10, 25, 50, 100]`.
- The table genuinely paginates 100 rows correctly — the underlying `effectiveRows()` signal and the rendered row count are both 100 (verified in `bilateral-results-list.component.spec.ts`, 78/78 passing per the `quick/` log entry).
- **But the rows-per-page dropdown control still visually shows "10."** This is user-visible and reported directly by Santiago Sánchez, who made the original 100-rows change.
- Root cause — `onecgiar-pr-client/src/app/shared/components/pr-table/pr-table.component.html:52-61` and the byte-identical markup in `pr-group-table.component.html:53-63` (citation as run, both files read this session):

  ```html
  @if (rowsPerPageOptions?.length) {
    <select class="pr-paginator__size" [value]="effectiveRows()" (change)="setPageSize(+$any($event.target).value)" aria-label="Rows per page">
      @for (opt of rowsPerPageOptions; track opt) {
        <option [value]="opt">{{ opt }}</option>
      }
    </select>
  }
  ```

  Both components bind a **native** `<select>`'s `[value]` to `effectiveRows()` (a computed `signal`, see `pr-table.component.ts:105` / `pr-group-table.component.ts:118`), with `<option>`s generated by an `@for` over `rowsPerPageOptions`. A native `<select>`'s `value` property can only "stick" to an `<option>` that already exists in the DOM at assignment time. When Angular sets `[value]` before — or without — that matching option being mounted/matched correctly in the generated list, the browser silently falls back to showing the **first** `<option>`, while the component's internal state (`effectiveRows()`, `pagedValue()`) stays correct. The pagination logic is right; only the visual selection is wrong.
- Why this is only visible now: **every other table in the codebase currently has `[rows]` equal to the FIRST entry of its own `rowsPerPageOptions`** (e.g. `rows=10` with options starting at 10, or `rows=20` with options `[20,50,100]`). Bilateral is the **only** table where the bound value (100) is not first in its options list (`[10,25,50,100]`) — which is exactly why this pre-existing defect in the shared component was invisible everywhere else and only surfaced here.
- Neither `pr-table.component.spec.ts` nor `pr-group-table.component.spec.ts` asserts the rendered `<select>`'s DOM value — both only assert `table.effectiveRows()` (confirmed: `grep -n "effectiveRows|select" pr-table.component.spec.ts` → lines 74, 77, 232 all assert the signal, never the DOM). Jest/jsdom cannot catch this class of bug today.

## 4. Proposed Outcome

The rows-per-page dropdown on every table in the system visually reflects the table's actual current page size at all times — on initial render with a non-default `[rows]` value, and after any user-driven page-size change.

## 5. Scope

- Fix confined to the two shared table components that own 100% of the system's rows-per-page dropdowns:
  - `onecgiar-pr-client/src/app/shared/components/pr-table/pr-table.component.ts` + `.html`
  - `onecgiar-pr-client/src/app/shared/components/pr-table/pr-group-table.component.ts` + `.html`
- Add a regression test per component that asserts the **rendered `<select>`'s DOM value**, not just the internal signal, covering the exact non-first-option case (`rows` not equal to `rowsPerPageOptions[0]`) that exposed this bug.
- The fix is expected to propagate automatically to all ~26 consumer tables (enumerated below) with no change to any consumer file.

## 6. Non-Goals

This is a real, separate issue (the client's own hard rule says "never a bare `<select>`/`<input>`" for interactive controls — `onecgiar-pr-client/CLAUDE.md` §5), but swapping the control is a materially larger, higher-visual-risk change touching the same 26 tables' chrome. Out of scope for this bug fix; log as follow-up tech debt.

## 9. Bug Diagnosis

### Observed Symptom

The bilateral results table correctly shows and paginates 100 results per page, but its rows-per-page dropdown control displays "10" instead of "100."

### Reproduction Steps

1. Open `/bilateral/:centerAcronym` (bilateral results list) with more than 10 results.
2. Observe the table renders 100 rows per page (confirms `effectiveRows() === 100`).
3. Look at the rows-per-page `<select>` in the paginator — it visually shows "10," the first entry of `rowsPerPageOptions=[10,25,50,100]`, not "100."
4. Expected: the dropdown shows "100." Actual: it shows "10."

### Root Cause (confirmed)

`pr-table.component.html:52-61` and `pr-group-table.component.html:53-63` (citation as run, both read in full this session) bind a native `<select [value]="effectiveRows()">` with `<option [value]="opt">` generated by `@for` over `rowsPerPageOptions`. Angular's `[value]` binding on a native `<select>` sets the DOM `.value` property; the browser can only honor it if a matching `<option>` is already present and matched at the time the property is set. Because every `<option>` is itself produced by the same change-detection pass via `@for`, and the parent's bound value is not necessarily the first rendered option, the native element falls back to displaying the first `<option>` in the list — a well-known Angular/native-`<select>`-with-dynamic-options ordering trap. The component's own pagination state (`effectiveRows()`, `pagedValue()`, `page()`) is unaffected and correct; only the DOM's visual selection is wrong. This is corroborated by the fact that **every other consumer table's `rows` value happens to equal `rowsPerPageOptions[0]`**, which trivially "fixes" the bug by coincidence everywhere except bilateral.

### Fix Strategy

Not a cosmetic one-liner (it requires correcting how the bound signal value is reconciled against dynamically-rendered native `<option>`s — a DOM/change-detection ordering fix, not a text/token tweak) → route to `/akili-specify bugfix/pr-table-paginator-dropdown-select` in **Lite** depth, Bug Mode, with a mandatory regression test asserting the rendered `<select>`'s DOM-visible value (not just `effectiveRows()`) for a non-first-option default in both `pr-table` and `pr-group-table`.

Candidate implementation approaches for `/akili-specify` to evaluate and finalize (not pre-decided here):
1. Imperatively sync the select's `.value` via `ViewChild` + `effect()`/`afterRenderEffect()` after options render.
2. Bind `[selected]` on the matching `<option>` (`[selected]="opt === effectiveRows()"`) instead of relying solely on the parent `<select>`'s `[value]`.

## 10. Approach Options

| Option | Description | Trade-off |
|---|---|---|
| A. `[selected]` on matching `<option>` | Add `[selected]="opt === effectiveRows()"` to each generated `<option>`; drop or keep `[value]` on the `<select>` as a secondary signal. | Simplest, idiomatic Angular fix for dynamic native `<select>` options; no `ViewChild`/lifecycle wiring. Still a native `<select>`, so still diverges from the "never bare native control" rule — acceptable since this is a minimal bug fix, not a redesign. |
| B. `ViewChild` + `effect()` imperative sync | Query the `<select>` element and imperatively set `.value = String(effectiveRows())` whenever the signal or options change. | Guarantees correctness even under edge-case change-detection timing, but adds lifecycle complexity (`afterRenderEffect`, ViewChild) for a problem Option A solves declaratively. |
| C. Migrate to `app-pr-select` / Spartan select | Replace the native `<select>` with the project's design-system select component. | Fixes the bug AND closes the "bare native control" rule violation, but is a materially larger change — new component contract, visual risk across 26 tables, likely needs its own proposal/spec, not a bug-fix-sized change. |

## 11. Recommended Approach

**Option A** (`[selected]` on the matching `<option>`) — it is the smallest safe correction that matches the actual defect (a native-select/dynamic-options binding issue), requires no new lifecycle wiring, and is trivially testable by asserting the rendered `<option>`'s `selected` state / the `<select>`'s `.value` in jsdom. Option C (migrating off the native control) is real tech debt worth tracking separately but is out of scope for a bug fix — flagged in Non-Goals.

## 12. Risks, Dependencies, And Open Questions

- **Risk:** a declarative `[selected]` fix must be verified to actually override jsdom/browser default-option fallback in Jest — the regression test is what proves this, not assumption. `/akili-specify` should design the test first (red before fix).
- **Risk:** because this is a shared component touching 26 tables, any regression here is maximally cross-cutting. The regression test must cover both `pr-table` and `pr-group-table`, and a manual/Cypress spot-check of bilateral (non-first-option case) plus one first-option-default table (e.g. results-list) is recommended before sign-off.
- **Dependency:** none — self-contained in the two shared files.
- **Open question:** none blocking. The native-`<select>` design-system violation is noted as accepted tech debt (Non-Goals), not an open question for this spec.
