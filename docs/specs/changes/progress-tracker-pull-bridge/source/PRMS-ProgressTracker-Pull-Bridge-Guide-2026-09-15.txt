Prepared by: Jose Berenguer, Technical Lead – AI, CGIAR System Organization

Date: 15 September 2026 · Version: 1.0 (draft for review) · Companion to: “Progress Tracker → PRMS on-ramp: the record, the five questions, and a proposed way forward” and the FAQ for Programs and Accelerators
In five lines
On 15 September the PRMS technical team and Jose agreed that the minimum product is two-way, and that the more valuable half is the pull: when a user is about to report on a KPI in the PRMS Reporting Tool, PRMS fetches the results the Progress Tracker can propose for that KPI (Héctor, Juan Carlos; Juan David: “the technical challenge is very low”).
That half now exists end to end as a working prototype: three read-only endpoints are live on the Progress Tracker Interoperability API (dev and staging; production off by flag), and a “Progress Tracker” source sits inside the Report form of an adjusted local copy of the PRMS Reporting Tool, built from the public code with synthetic data, on the current upstream look and feel.
The operating model is pull → check → confirm → pre-fill → the user presses Create. The API never writes to PRMS; nothing is saved until the user creates; a person finalises every result; PRMS remains the system of record; pooled Window 1/2 programs only — the same story as the FAQ and the on-ramp document.
Getting started is one GET — …/dev/api/prms/indicators/{indicator_id}/results — with interactive documentation at …/dev/docs. A first draft for a KPI with evidence costs about US$0.01 and 20 seconds; every later call is served from cache in 0.2 s. Sections 4 to 7 give the URLs, real responses, the field table and the numbered port list for the real Reporting Tool.
What remains is listed as decisions versus work in section 8 (API key, production flag, ownership of the indicator ids, duplicate check, evidence coverage, prompt tuning, TEST before PROD, FAQ co-sign). Hosting the whole PRMS copy in the cloud, should it be useful, is about 1.5–2.5 days and US$60–110 a month (section 9).

2. The operating model

Figure 1 — The pull in six steps: the user starts and ends in PRMS; the Progress Tracker is only read
The user never leaves the PRMS Reporting Tool. On the Reporting tab they open the KPI they want to report and press Report, as today. Inside the Report form, next to the existing entry mode, there is a source called Progress Tracker. Opening it asks the Progress Tracker for the results it can propose for that KPI; the user reads them, opens the details (which evidence supports the draft, why this result type, what is still missing), and presses Use this result. The free-text fields of PRMS’s own create form — title, description and, where the KPI leaves it open, the result type — are pre-filled and left unsaved for review. The result exists only when the user presses PRMS’s own Create and continue; it then lands exactly where any manually created result lands, in Editing, owned by the Science Program, labelled W1/W2.
Stated plainly, and consistent with the FAQ (questions 3, 6, 9 and 10) and the on-ramp document:
The API never writes to PRMS. The Interoperability API only answers GET requests. The only thing it stores on its own side is a cache of the drafts it produced, keyed on the evidence it saw.
Nothing is saved until the user creates. Pre-fill is not creation. A user can look at the proposals, use one, change their mind and choose another, or ignore them all and type by hand.
A person finalises every result, through the normal PRMS workflow: complete the sections, validate, submit, QA.
PRMS remains the system of record. The Progress Tracker keeps evidence and drafts; it does not keep a copy of the result.
Pooled Window 1/2 programs only. The Progress Tracker’s indicators come from the PORBs, which contain only W1/W2 data.
Because the result is created by PRMS’s own Create action, the question raised on the call — whether pulled results should land in Editing or Pending Review — disappears: they land where PRMS puts a result created by that user. The push door discussed since June (registering the Progress Tracker as a platform with its own key and keep_editing, both shipped by the PRMS team on 27 August and 10 September) remains the Alliance’s item (a); this document is item (b).
3. Architecture

Figure 2 — Architecture: the PRMS server proxies one read-only call to the Interoperability API; the write to PRMS happens only when the user creates
Three moving parts, two of which already exist in the real PRMS code base:
PRMS Reporting Tool, Angular client. The Report form gains one source component (“Progress Tracker”) that lists proposals and pre-fills the form. It talks only to the PRMS server.
PRMS Reporting Tool, NestJS server. A small progress-tracker module proxies the call server-to-server, exactly like the existing cgspace-discovery module proxies CGSpace, MELSpace and WorldFish: base URL and API key from environment variables, a whitelisted query, a 25 s timeout, and a classified status (ok, not_found, unavailable) so the client never sees an upstream error message or host.
Progress Tracker Interoperability API (FastAPI on AWS Lambda behind API Gateway, eu-central-1; repository cgiar-ppu/progress-tracker-interoperability-api). A new prms_pull router with three routes reads the Progress Tracker’s reference and evidence tables (DynamoDB), extracts text from the evidence files (S3), asks a small model (Claude Haiku 4.5) for PRMS-shaped drafts, and caches the answer. Feature-flagged: PRMS_PULL_ENABLED is on for dev and staging and off for production.

4.2 GET /api/prms/indicators/resolve — from PORB texts to the Progress Tracker id
Purpose. Let PRMS find the Progress Tracker’s indicator_id from the PORB fields it already displays, without computing the hash itself (section 5 explains the formula and why the server-side path is safer). Query: program (name) or program_id; aow, center, hlo_title, description; optional kpi_type as a tie-breaker. At least one of hlo_title or description is required (422 otherwise); 404 when the program is unknown.

4.4 Errors, edge cases, timing and cost
Situation
What happens and what PRMS should do
Unknown indicator_id, or the flag is off in that environment
HTTP 404. The prototype’s PRMS module maps it to not_found and the form shows “this KPI is not known to the Progress Tracker” with the Manual entry escape
Bad query value (e.g. max_results=20)
HTTP 422 with the validation detail
KPI without evidence
HTTP 200, mode=template, fallback_reason="no_evidence", one placeholder per result type, 0.2 s, not cached
mode=template requested
HTTP 200 with the placeholder, instant and free — useful to render immediately and upgrade later
Model failure, time-out or nothing usable
HTTP 200, mode=template with the error text in fallback_reason; nothing is cached; PRMS can retry (Refresh)
Cache
One model call per (indicator, evidence fingerprint). The fingerprint changes when submissions, files, notes, prompt version, model or max_results change; refresh=true bypasses it. No time-to-live
First call on a rich KPI
20–22 s measured on the 13-item KPI (cold start ≈ 2 s, file extraction 3–4 s, model 13–15 s). The Lambda keeps the whole call inside the 29 s API Gateway limit (extraction capped at 9 s, model gets the rest, template fallback on time-out). Client time-out ≥ 30 s
Cached, template, resolve, ready-counts
0.2–0.7 s
Cost of a fresh draft
3,134 input + 1,364 output tokens on the 13-item KPI = US$0.0099 at Claude Haiku 4.5 list price (US$0.0113 with the first prompt version; US$0.0107 on staging). Cached and template calls cost no model tokens
What the API reads and writes
Reads the Progress Tracker’s reference and evidence tables and the evidence files (first 3 pages of a PDF, ≤ 6 files, ≤ 8 MB each, images not read, URLs cited not fetched). Writes only its own cache row and one audit row per generation. Never writes to PRMS

5. Mapping the KPI

Figure 3 — Mapping a PRMS indicator row to the Progress Tracker id: same PORB texts, one deterministic hash, two ways to obtain it
The Progress Tracker keys every KPI as indicator_id = md5("{program}|{aow}|{center}|{hlo_title}|{description}") truncated to 12 hexadecimal characters, computed over the PORB master texts (the same formula the Progress Tracker’s reference seed uses; program id = md5("PROGRAM|{name}")[:12]). The 2026 Reporting tab of PRMS shows the same PORB rows — for Breeding for Tomorrow, AOW01 lists 22 KPIs in both systems and the row texts are the PORB activity descriptions — so the composite key can be rebuilt from what PRMS already holds: the program name, the AoW as "AOW01: <name>", the Center label as written in the PORB (CIAT (Alliance), Bioversity (Alliance), AfricaRice, CIMMYT …), the HLO title and the indicator description.
Two ways to obtain the id, both supported:
Compute it locally — deterministic, no call. Caveat: about 16 PORB rows collide on those five fields (same texts, different KPI type); the Progress Tracker re-keys those siblings through a disambiguation table, so a local hash can point at the wrong sibling.
Call /resolve once per row, server-side, and store the answer — the recommended path. It returns exact when the hash matches, fuzzy when PRMS’s row label differs cosmetically (prefixes, truncation, upper case), and always a short candidates[] list with the KPI type for a picker. The example in section 4.2 resolved a PRMS-style row label with score 0.878.
Recommendation: PRMS stores the Progress Tracker id on its ToC indicator rows. In the adjusted local copy this is what makes the whole flow need no extra code: the id sits on the indicator row (related_node_id and toc_result_indicator_id of toc_results_indicators), the Report form already carries indicators[0].related_node_id into the create payload, and PRMS’s own framework create stores it in results_toc_result_indicators.toc_results_indicator_id — verified on the result created in section 6, which carries 5d51da6c6916. In the real ToC catalogue that column holds the ToC node identifier, so the PRMS team would add a column (or a side table) for the Progress Tracker id and fill it once per reporting year with /resolve; when PORB texts are refreshed the ids change and the rows must be re-resolved (ownership of that step is a decision in section 8).

Everything below exists in the adjusted local copy, every changed line tagged // PT-BRIDGE, and can be handed over as one PR-shaped diff against the Reporting Tool (nothing has been pushed to any Alliance repository). The numbering follows the order of work.
Server module — copy src/api/progress-tracker/ (6 files, 607 lines: module, controller, service, two query DTOs, unit tests) and register it in src/api/modules.routes.ts ({ path: 'progress-tracker' }) and src/app.module.ts. Browse component — copy pt-results-browse/ (4 files, 810 lines) next to kp-cgspace-browse; standalone, injects only the API service; handles the five states (loading, results, empty, error, pre-filled banner).
Host form — apply the lab-report-form hunks (≈160 lines TypeScript, ≈116 lines template): the source switch “Manual entry | Progress Tracker” for non-KP indicators, the third tab for KP indicators, the panel, the onPtResultSelected mapping (title cut at 30 words with a notice, description, type only when the KPI leaves it open, handle for knowledge products), the optional description field, and the reset on re-arm. Payload utility — a two-line hunk so toc_progressive_narrative travels in the create payload (the server DTO already accepts and stores it; no server change).
Where the id lives — add the Progress Tracker id to the ToC indicator rows (section 5), filled by /resolve once per reporting year; read it where the prototype reads indicators[0].related_node_id (one computed property).
States to handle — all already in the component: loading (up to ≈ 20 s on a cold KPI, or call mode=template first), results, empty, not_found (unknown id or flag off), unavailable (time-out, network, 5xx, unconfigured) with the “use Manual entry” escape, and the post-pick banner. Effort, honestly. A port into the real code base is more than that — review, the team’s lint hooks, a pull request, QA on PRMS TEST, the id column and its fill — and that sizing belongs to the PRMS team; the tagged diff is meant to make it a reading exercise rather than a design one.

9. Hosting the PRMS prototype in the cloud

Figure 9 — A demo-grade cloud shape for the adjusted local copy: one instance, one managed database, basic-auth edge, pipeline from GitHub
For this round no hosted copy is needed: the Alliance receives the endpoints, this guide and the screenshots, and the prototype is demonstrated live from Jose’s own environment. Should a hosted copy become useful (for Nicoleta, or for the PRMS team to click through without a call), the assessment is:
Shape. What upstream ships is a modular monolith: the server runs either as a Node 20 container or as a Lambda behind API Gateway; the client is a static Angular build served by nginx; the database is managed MySQL. The cheapest faithful shape for a demo is one small EC2 instance (t4g.medium) running docker-compose with four containers — web, API, normalizer, an authentication stub — a single-AZ RDS MySQL 8.0 (db.t4g.small), an nginx or ALB edge with basic authentication and a TLS certificate on a synapsis-analytics.com sub-domain, and GitHub Actions deploying through an OIDC role and CloudFormation.
Effort. 1.5–2.5 days: half a day for compose, the proxy locations and the production client build; half a day for the CloudFormation, role and pipeline; half a day for the data restore and smoke test; half to one day for surprises.
Cost bracket (eu-central-1, always on): RDS ≈ US$30, instance ≈ US$27 (Fargate ≈ US$50 if preferred), ALB ≈ US$20 unless the existing edge is reused, logs and egress ≈ US$5 — ≈ US$60–110 a month, ≈ US$30–40 if stopped outside demo hours.
The three hard bits. (1) The Reporting tab reads a ToC catalogue that is fed by the Alliance’s ToC tooling, not by the code base — our seed for Breeding for Tomorrow is the only source, so any “real-looking” demo beyond that program means extending the seed. (2) The database cannot be rebuilt from migrations alone; it must be restored from the current dump and only new migrations replayed. (3) Everything external is stubbed — single sign-on, CLARISA validation, CGSpace/MELSpace/WorldFish discovery, repository metadata, evidence storage, messaging, e-mail — so each is a network decision and a “this button shows an error state” caveat in the demo script; exposing the copy to Alliance colleagues also needs a governance decision on basic authentication versus single sign-on.
Does PRMS’s architecture make hand-over easier? Yes on the server side: the discovery-proxy pattern (cgspace-discovery) is a clean, self-contained “external source” module that a progress-tracker module copies one to one, and the framework create endpoint already accepts the indicator context, so no schema change was needed. Less so on the client: the Report form is one large component with the knowledge-product-only tab pair, so adding a source for non-KP result types is a small structural change to that form — kept tagged and hand-over friendly as a single pull request.
Annex A — Glossary
Term
Meaning in this document
Progress Tracker
The CGIAR Progress Tracking Solution: optional, year-round evidence capture against PORB KPIs for Programs and Accelerators (pooled W1/W2)
Interoperability API
The Progress Tracker’s public API (AWS Lambda + API Gateway, eu-central-1) used by Centers’ MEL systems and, now, by PRMS
Pull
PRMS asks the Progress Tracker for proposals when a user reports; nothing is pushed into PRMS
Push (on-ramp door)
The Progress Tracker creates a draft result in PRMS through PRMS’s ingestion API with a platform key — the July concept, item (a) of the 15 September MVP
KPI · indicator
One PORB row (program, area of work, Center, high-level output, description, type, target); indicator_id is its 12-character key in the Progress Tracker
PORB
Plan of Results and Budget — the one-year slice of the Theory of Change from which both systems take their KPIs
Draft · proposal
One PRMS-shaped result the API proposes for a KPI, drafted by a small model from the evidence attached to that KPI
Template
The placeholder returned when a KPI has no evidence or drafting failed; always available, never cached
Evidence fingerprint
A hash of the evidence a draft was made from; the cache key and the duplicate-detection key
Editing
PRMS’s status for a result created but not yet submitted; where a result lands when a user presses Create
Adjusted local copy
The PRMS Reporting Tool and normalizer run locally from the public repositories, on synthetic and public reference data, with no connection to any CGIAR system
